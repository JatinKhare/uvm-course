## 2. Items

`mcpu_mem_item` extends the Module 03 preload item with a `kind` field:

- `rand kind` ∈ {`PRELOAD`, `SET_LATENCY`, `FAULT_NEXT`} — what the driver does with the item.
- `rand bit [31:0] addr, data` — used by `PRELOAD` (write a word into the model) and `FAULT_NEXT` (`addr` = address whose next access is faulted).
- `rand int unsigned lat_min, lat_max` — used by `SET_LATENCY`; constraint `lat_min inside {[1:4]}; lat_max inside {[lat_min:4]};`.
- `c_align`: `addr[1:0] == 0`.

Items do **not** carry responses: responses are generated by the driver from the bus requests.

## 3. Driver behaviour

Two concurrent threads in `run_phase` (started with `fork ... join_none`), sharing the model:

```
// Thread R: responder (autonomous; never waits for a sequence)
forever @(posedge vif.clk):
   if rst_n && ls_req && !busy:            // new request seen
       latch addr/we/wdata; busy = 1; lat = pick(cfg.lat_min, cfg.lat_max)   // latch latency NOW
       count down lat-1 more edges
   when count done:
       if we: model.write(addr, wdata) else rdata = model.read(addr)
       vif.ls_rvalid <= 1 (one cycle), vif.ls_rdata <= rdata;  busy = 0
   // a held ls_req may start the next access on the edge right after the response (back-to-back)

// Thread C: control (blocking is fine here)
forever: seq_item_port.get_next_item(req);
         case (req.kind) PRELOAD: model.write(...); SET_LATENCY: cfg.lat_min/max = ...; FAULT_NEXT: fault_set.insert(addr);
         seq_item_port.item_done();
```

Why autonomous responses: a memory must answer the CPU whenever it asks, even if no sequence is currently queued. A single loop built on blocking `get_next_item` would stall the bus whenever the sequence is idle; `try_next_item` polling in the same loop is the alternative, but two threads separate "respond now" from "change behaviour" cleanly. Handshake: `get_next_item`/`item_done` appear only in thread C, with one `item_done` per item.

## 4. Monitor

The Exercise 01 monitor, unchanged, in both modes. Passive mode: the agent builds only the monitor; no driver/sequencer exist; some other model answers the bus and the monitor reports completed accesses.

## 5. Config object (defaults)

`vif` (set by test), `is_active = UVM_ACTIVE`, `lat_min = 1`, `lat_max = 1`, `mem_base = 32'h0`, `mem_size`, `uninit_policy` ∈ {`ZEROS`, `PATTERN`, `ERROR`} (default `PATTERN` with a recognisable word, so uninitialised reads are visible), `mem` (handle to `mcpu_mem_model`, created by the agent and exposed so a test can `write`/`read` directly — "visible to tests").

## 6. Hazards

- **Preload vs CPU start:** a test preloads through the model handle (zero-time, e.g. in `start_of_simulation_phase` or before reset release) or through `PRELOAD` items completed by a virtual sequence before reset is released (Module 03 pattern). Either way the CPU never meets uninitialised memory.
- **Latency changing mid-access:** latch the latency when the request is accepted; `SET_LATENCY` affects only later accesses.
- **Same-edge ordering:** thread R and the monitor both sample at the edge; R drives responses with non-blocking assignments after the edge, so the monitor sees `ls_rvalid` on the edge the DUT does.
- **Back-to-back:** `busy` is cleared on the response edge and the next request is accepted on the following edge (`ls_req` held high).

## Interface gap (error injection)

`mini_cpu_if` has **no error-response signal**, so `FAULT_NEXT` cannot be expressed on the bus as defined. Honest options: (a) add an `ls_err` signal to the interface once, in Module 10, together with the exception behaviour of the DUT stub (a change to a shared name, recorded in `PROGRESS.md`); (b) model a fault as "no response" (the DUT stalls) — a different test with a different expected result. This design keeps `FAULT_NEXT` as a placeholder item kind that does nothing until (a) is decided. Do not invent a signal in a testbench that the DUT does not have.

## The result that matters

For a master-initiated bus, the agent on the *slave* side must be reactive: responses are driven by bus events, and sequences only change the slave's behaviour (data, latency, faults). Putting responses in sequence items forces the sequence to know cycle timing and makes the bench stall when the CPU asks and nothing is queued.
